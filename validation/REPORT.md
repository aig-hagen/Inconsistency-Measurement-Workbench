## Test data

- **1000 knowledge bases** (`data/kbs.txt`, generated by `gen.cjs` with fixed seeds): 1–8 formulas (mean 4.5), 1–5 atoms, formulas of depth ≤ 3 over all connectives (¬, ∧, ∨, →, ↔, ⊤, ⊥, and ⊕ over literals inside other formulas, because the original Java code fails on other uses of ⊕). 363 of the bases are consistent. Each base is written in TweetyProject syntax and parsed by both implementations; the Java side parses it again for every measure because some Java implementations modify formulas.
- **300 knowledge bases with exclusive or** (`data/kbs-xor.txt`, `gen-xor.cjs`): 1–7 formulas over 1–4 atoms in which ⊕ also occurs at the top level and over arbitrary operands (only compared with the fixed sources).
- **1000 CNF instances** (`data/cnfs.txt`): 400 random 3-SAT near the phase transition (20–150 variables), 300 random mixed-length CNFs, 200 small random CNFs, 25 pigeonhole, 25 parity and 50 graph-colouring instances.
- Per-measure time limit on the Java side: 10 s, and every computation that timed out was repeated with 60 s (Iceberg 5 s; patched FB and Shapley 60 s). The remaining Java timeouts are excluded from the comparison and listed. The JavaScript side computes all 1000 × 36 values in about 10–40 s (depending on the load of the machine).

Values are compared exactly (relative tolerance 10⁻⁹), with 10⁻⁶ for η, CC, CSP and Shapley values (simplex / GLPK output precision) and 10⁻³ for the fuzzy measures (numerical optimisation on both sides). Infinity and NaN must coincide.

### Forgetting-based measure (FB)

`Implication.clone()` in TweetyProject returns a new implication that **shares the operand pair** of the original (`new Implication(this.formulas)`), and `Implication.replace()` modifies the clone with `setFirstFormula` / `setSecondFormula`. `FbInconsistencyMeasure` calls `replace()` on the conjunction of the knowledge base while it searches for the substitutions, so the implications of the knowledge base itself are changed during the search and later candidates are tested against corrupted formulas. This produces wrong values (and NullPointerExceptions in the SAT interface) whenever a knowledge base contains implications.

- Original Java: 647 equal, 15 equal by convention (Integer.MAX_VALUE vs ∞), 39 different, 67 exceptions, 232 timeouts. Examples:
  - KB 0 `!a ; a ; (!b||b||a)&&(b=>a)&&(a=>a) ; b ; (b&&b)&&(!b&&!a)`: Java 2, JS 3
  - KB 23 `b&&c ; !(!b) ; c ; !(b||-)||!(!b=>!c) ; !a ; !b&&(!c||b) ; a`: Java 2, JS 3
  - KB 31 `a ; !(!a) ; !a&&!a ; a&&(+=>a)`: Java 2147483647, JS 2
  - KB 53 `!c&&c ; a||!b||!b ; (b||(!c=>!a))&&((b&&!b)&&(a=>!a)) ; !(!b) ; b||!b||!c ; !c`: Java 2, JS 3
  - 66 × `NullPointerException: Cannot invoke "java.lang.Integer.intValue`
  - 1 × `NullPointerException: null`
- Java with **only** `Implication.clone()` fixed (`validation/java/patched`, a copy compiled in front of the original sources): 759 equal, 18 equal by convention, 0 different, 71 exceptions, 152 timeouts (the corrected Java search is slower because it no longer stops early on corrupted formulas).
- All 71 remaining exceptions occur in bases containing `^^` and come from a second, independent defect: when FB substitutes ⊤ or ⊥ for an atom inside an exclusive or, `ExclusiveDisjunction.toCnf()` leaves a negated constant (e.g. `!-`) inside a clause, and `Sat4jSolver.isSatisfiable` (line 102) fails with a NullPointerException because it expects only negated atoms there.

The JavaScript port computes the measure with a SAT encoding (one selector per atom occurrence and a cardinality bound) and returns ∞ where the Java code returns `Integer.MAX_VALUE` (a ⊥ that cannot be forgotten).

The Java implementation has several defects, and the port implements the documented intention instead:

1. **Order-dependent *-mapping.** A candidate set C is a *-conflict if every formula of C is needed to derive some formula of a minimal inconsistent subset ("we can find … a mapping that ensures that every part of candidate is used"). Java computes one minimal entailing subset per formula greedily, removing formulas in `HashSet` iteration order, and fails when that particular choice does not cover C. The port checks whether *some* choice of minimal entailing subsets covers C. With the identity operation the minimal entailing subsets are unique, which is why that variant agrees completely. Renaming the atoms of the knowledge bases (a→p, b→q, …), which cannot change any inconsistency value, changes the Java result on 27 of 60 knowledge bases with a difference (classical consequence; e.g. KB 20: 3 before, 2 after renaming), confirming that the Java value depends on hash codes. The port returns the same value for the original and the renamed base in all 60 cases.
2. **Conjuncts.** `getConjuncts()` collects the suffixes c_i ∧ … ∧ c_k of a conjunction (so `a` is not a conjunct of `a && b`), contradicting the documentation ("{a, b, a&&b} for a&&b"), and both conjunct operations ignore formulas that are neither conjunctions nor literals. The port uses all sub-conjunctions plus the formula itself.
   To separate the two effects, the port has a validation-only switch (`javaCompat`) that reproduces TweetyProject's conjunct sets exactly while keeping the existence check of item 1. With it, *conjuncts* agrees on 618 of 618 bases and *smallest conjuncts* on 611 of 626; the remaining 15 differences are bases where a formula is a conjunct of several formulas, so that Java's greedy choice matters (item 1).
3. **Opposite literals** throws a `ClassCastException` (a `HashSet` is cast to `PlBeliefSet`) as soon as it has to check a literal; on all other bases the values agree.
4. **Modus ponens** loops forever as soon as an implication fires (`changed` is set on every pass); it is therefore not run on the Java side. The port computes the fixpoint.
5. **Prime implicants** are compared syntactically in Java (conjunctions built from hash sets), and `toBlakeCanonicalForm()` throws for some formulas; the port compares prime implicants as sets of literals. The values agree wherever Java returns one.

## SAT solver

The CDCL solver (`src/core/03-sat.js`) against Sat4j 2.3.5 (`SolverFactory.newDefault()`) on the 1000 CNF instances: **1000 of 1000 verdicts agree**; all 387 models returned by the port satisfy their formula (387 checked); 304 of 304 instances with ≤ 20 variables also agree with exhaustive enumeration.

## Not compared with the original sources

- **Postulates**: TweetyProject checks each postulate on one instance chosen via `Random(hashCode)` of the canonical ordering, which cannot be reproduced; the port checks all derived instances. The original `ImSafeFormulaIndependence` adds the safe formula (already contained) instead of removing it and can never fail; the port removes it, as do the fixed sources.
- **Iceberg with modus ponens**: the original Java code does not terminate; compared with the fixed sources above.
- **Exclusive or at the top level or over complex operands**: the original `Sat4jSolver` throws a `ClassCastException` for any formula `a ^^ b` at the top level (`ExclusiveDisjunction.isClause()` is true but it is not a `Disjunction`) and a `NullPointerException` for operands that are not literals (`toCnf()` returns no CNF), so all SAT-based Java measures fail; `data/kbs.txt` therefore uses ⊕ only over literals inside other formulas, and the general case is compared with the fixed sources on `data/kbs-xor.txt`.
